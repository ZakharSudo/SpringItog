**Система бронирования отелей (микросервисная архитектура)**

**О проекте**

REST API для бронирования отелей, реализованное на микросервисной архитектуре с использованием Spring Cloud. В проекте реализованы: аутентификация на основе JWT, распределённая транзакция (паттерн Saga с компенсацией), автоматический подбор номеров с учётом загруженности и API Gateway.

**Архитектура и компоненты**

Проект включает 4 независимых модуля:

- **eureka-server** (порт 8761) — Service Discovery (реестр сервисов).
- **api-gateway** (порт 8080) — единая точка входа, маршрутизация запросов и передача JWT.
- **hotel-service** (порт 8081) — управление отелями и номерами, ведение статистики загруженности (timesBooked), хранение блокировок дат.
- **booking-service** (порт 8082) — регистрация и авторизация пользователей, управление бронированиями, оркестрация Саги.

**Инструкция по запуску**

Для запуска системы нужно последовательно запустить 4 приложения (например, через IntelliJ IDEA):

1. EurekaServerApplication
2. HotelServiceApplication
3. BookingServiceApplication
4. ApiGatewayApplication

После запуска Eureka доступна по адресу: http://localhost:8761
Документация Swagger (Hotel): http://localhost:8081/swagger-ui/index.html
Документация Swagger (Booking): http://localhost:8082/swagger-ui/index.html

**Основные эндпойнты (через API Gateway на порту 8080)**

- POST /user/register — регистрация пользователя (по умолчанию роль USER).
- POST /user/auth — авторизация и получение JWT-токена.
- GET /api/hotels — получить список отелей (доступно без токена).
- GET /api/rooms/recommend — получить рекомендованные номера (сортировка по возрастанию times_booked и id).
- POST /bookings — создать бронирование. Поддерживает автоподбор (autoSelect: true).
- POST /api/hotels — создать отель (только для роли ADMIN).

**Реализация паттерна Saga (согласованность данных)**

При создании бронирования Booking Service выполняет следующие шаги:

1. Создаёт локальную запись со статусом PENDING.
2. Отправляет запрос в Hotel Service (через OpenFeign) для подтверждения доступности дат.
3. При успехе: статус меняется на CONFIRMED, а в Hotel Service инкрементируется счётчик timesBooked и создаётся блокировка.
4. При ошибке (409 Conflict): статус меняется на CANCELLED, вызывается компенсирующий эндпойнт /release для снятия блокировки. Идемпотентность обеспечивается передачей requestId.

**Тестирование**

В корне проекта находится файл requests.http с готовыми запросами для проверки:

- аутентификации и ролей (USER / ADMIN);
- успешного создания бронирования с автоподбором;
- обработки ошибки 409 (номер занят) и срабатывания компенсации;
- валидации дат (ошибка 400).
